## 1. 项目概述

### 1.1 背景与痛点

企业在系统数量增多后普遍面临：

1. **业务路线不透明**：一条业务从开始到结束，实际走哪些系统、库、部门？靠人脑记忆，问一个人一个说法。
2. **多条路线说不清**：同一起终点往往有多条可走路线（默认/备选/特殊场景），没人画出来。
3. **出问题不知道卡在哪**：流程走到某节点停了、没走到终点，是哪个环节？人工逐环节排查很慢。
4. **环节耗时不可见**：每环节花多久、哪条路线最慢、瓶颈在哪，没有数据。
5. **数据准确性难核实**：某个环节数据对不上，涉及哪些数据流、该查哪个库表，缺少线索。
6. **知识断层与变更风险**：核心流程知识在人脑里，人走即断；改动某个环节影响哪些路线，说不清。

### 1.2 产品愿景（血管网类比）

> **错综复杂的血管网 = 关系网；血液流向 = 数据/业务流向；血栓 = 出问题的环节；顺藤摸瓜 = 从问题环节逆血流找源头、顺血流看影响。**

把系统、数据库、部门、业务环节画成一张**像血管系统一样错综复杂但脉络清晰**的关系网，给同一起终点提供**多条路线**，并在系统出问题时**顺着关系网把根因和影响面摸出来**。

### 1.3 核心定位（三大核心）

| 核心 | 含义 | 一句话 |
| --- | --- | --- |
| **陈列** | 节点关系网的展示 | 把错综复杂的血管网画清楚 |
| **择路** | 多条路线的选择 | 同一起终点给多条路线、可对比 |
| **摸瓜** | 顺藤摸瓜式问题排查 | 从问题环节找到源头和影响面 |

其余一切能力（检测点、实例、卡点、耗时、告警、工单、看板）都是**服务于"摸瓜"的信号源与工具**。

## 3. 核心能力需求

### 3.1 核心一 · 陈列：节点关系网的展示

- 4 类混合站点作节点：系统/子系统、数据库/表、部门/岗位、业务动作/事件（制造场景预留设备/工序/工位）
- 有向连线表达流向，支持**分岔与汇合**（血管主干 + 分支）
- 力导向自动布局、节点拖拽、缩放/平移/全屏
- 点击节点 → 详情（属性、上下游、所在路线）
- 一键高亮某节点**全部上下游**；搜索 / 类型过滤 / 按流程切换
- 复杂时**折叠 / 展开**子网

### 3.2 核心二 · 择路：多条路线的选择

- 流程（起点→终点）下，从路网定义多条**完整路线**，标优先级：**默认 / 推荐 / 备选**
- **路线视图**：一条路线按站点顺序串联（一条地铁线）
- **路线对比**：并排对比站点构成、长度，高亮共享/差异站点
- **任意两点路径查询**：A→B 有哪几条走法

### 3.3 核心三 · 摸瓜：顺藤摸瓜式问题排查 ⭐

```
▸ 点击问题站点 → 图上高亮它所有关联（上下游全亮）
▸ 向上摸藤（溯源）：数据/业务从哪来？上游站点带检测点状态，可疑者标红
▸ 向下看瓜（影响）：影响哪些下游、哪些路线、哪些业务单号
▸ 多路线视角：这个站在哪几条路线上，各影响多大
▸ 排查建议：按"最可疑→最无关"排序，引导一步步定位根因
```

- 排查轨迹留痕、可回退；实例排查全程用**业务别名**标注便于记忆
- 配套**业务单号全局反查**：输入单号/显示名/别名 → 直接定位实例当前卡点

## 5. 模块划分与功能需求

### 5.1 模块总览

| 模块 | 职责 |
| --- | --- |
| 数据接入模块 | 外部数据图来源统一接入（连接器可插拔） |
| 建模模块 | 流程/站点/路网/路线编辑维护 + 版本留存 |
| 监控排查模块 | 实例追踪、卡点定位、检测点、顺藤摸瓜 |
| 分析模块 | 路线对比、路径查询、影响面、溯源、耗时 |
| 告警+工单模块 | 等级驱动预警/干预、通知、工单跟踪 |
| 配置版本模块 | 全配置版本留存/对比/回滚/审批 |
| 开放 API 模块 | 对外查询/上报/触发接口 |
| 看板报表模块 | 状态看板、管理报表、大屏 |

### 5.2 数据接入模块（独立模块）

- **数据池（连接器可插拔）**：数据库连接独立成数据池模块——支持 MySQL 8 / PostgreSQL / H2（方言可插拔，后续可加 Oracle 等）；管理员在「数据接入」页**可视化**新增/编辑/测试连通/切换当前连接/浏览库表/数据预览；连接器密码 AES 加密存储；配置存平台库，预留分布式拓展（多节点共享配置、各自建连接池）
- 连接器类型：DB（当前）｜ Excel/CSV 导入、CMDB/资产 API、日志解析、IoT/设备（远期）
- 流程：创建连接 → 测试 → 采集任务（手动/定时）→ 生成候选 → 映射确认 → 入库 → 采集日志 + 变更检测（新库/新表提醒）
- 映射规则可配置：如"外部表名 = 站点名""库名 = 归属系统"

### 5.3 监控排查模块（核心）

- 检测点：默认（按站点类型自动生成：库→数据量/新鲜度/延迟；系统→状态/心跳；动作→完成/耗时）+ 自定义（阈值 / SQL / 脚本）
- 实例追踪：一次真实运行 = 实例，记录每站到达/离开/耗时/状态
- 卡点定位、耗时分析、数据核实、顺藤摸瓜排查、业务单号反查

### 5.4 告警+工单模块

- 等级驱动预警/干预（见 6.3）；通知渠道：站内 + 邮件（钉钉/企微远期）
- 工单：告警→工单，指派责任人、跟踪 OPEN/PROCESSING/RESOLVED

### 5.5 配置版本模块

- 对象：流程/站点/路线/路网边/检测点/接入配置
- 留存最近 N 版 + 改动记录（谁/何时/改了什么/diff）+ 对比 + 回滚
- 高等级变更可配置审批（DRAFT/PENDING_APPROVAL/PUBLISHED/ROLLED_BACK）

### 5.6 开放 API 模块

- 对外 REST API：上报实例、查询流程/站点/路线、触发检测、获取告警
- 鉴权：API Token；用途：外部系统集成、实例自动采集通道

## 6. 核心概念与数据模型

### 6.1 领域模型

```
场景 Scene（数据流 / 业务流程 / 制造流程·远期）
 └─ 流程 Process（起点→终点，带等级）
     └─ 路网：站点 Node（带等级）+ 有向边
         └─ 路线 Route（优先级 + 等级）
             └─ 实例 Instance（业务单号 + 业务别名）
                 └─ 每站到达/离开/耗时/状态
                      └─ 检测点 Checkpoint（带等级）→ 检测结果 → 告警 → 工单
```

### 6.2 命名与别名体系

- 所有对象（关系网/流程/路线/实例/站点/检测点/告警）支持 **1 个主显示名 + 多个别名**
- 界面默认显示主名，详情/悬停显示单号；全局搜索**单号 + 显示名 + 别名通吃**
- 通用 `alias` 表 + `instance.biz_name`；支持批量导入别名

### 6.3 版本与等级体系

等级打在流程/站点/路线/检测点上：

| 等级 | 版本管控 | 预警策略 | 干预策略（三动作组合） |
| --- | --- | --- | --- |

## 15. 图来源与自动/半自动分析（v1.2 新增）

> 本章为 2026-08-16 讨论新增，定义「关系网图来源」的自动/半自动分析能力，覆盖三件事：**图怎么来**（三条路线）、**图怎么用**（三层视图）、**越用越准**（校正闭环）。本章是后续实现基准；标注「建议/待评审」的条目为默认方案，可评审调整后执行。

### 15.1 定位与目标

平台在「人画关系网」之外，新增「**自动/半自动分析出图**」能力：

- 以**自动分析为基础**、**人为校正为准**，最终实现业务**全面网图展示、条理清楚**，为「对症下药、快速排查」打底。
- 三条分工底线：**引擎定骨架、大模型管语义、人拍板**。
- **不接大模型，平台照常工作**（引擎 + 人工闭环，一条腿都不瘸）。

### 15.2 图来源三条路线（入口处选择一条）

| 路线 | 说明 | 素材 |
| --- | --- | --- |
| **① 引擎分析**（主干） | 连库扫描 → 单据识别 → 流程还原，自动出底图 | 数据库结构 |
| **② 大模型分析**（增强） | 大模型直接以原始素材为输入，提炼语义关系出图 | 库结构 / 界面入口 / 导入文档（E-R 图等） |
| **③ 人工创建**（兜底） | 纯手工画图 / 导入 E-R 图等文件解析成图 | 人工 / 文件 |

三条路线产出的都是**草稿/提案**，统一汇入人工校正（见 15.6）。

### 15.3 引擎分析机制（路线①）⭐ 单据模式库

**目标**：对任意业务库自动识别「单据与流转」，产出草稿图。引擎不靠认识某个特定系统，而靠一套**通用业务单据模式库**——绝大多数业务系统（HIS / MES / ERP / 教务）骨子里是同一类形状，引擎只认这些「规律」：

1. **单据主表识别**：有主键 + 业务编码号（挂号单号 / 工单号 / 学号）
2. **状态字段识别**：字段值随流程变化（待缴费 → 已缴费 → 已退费）
3. **时间字段识别**：记录各步发生时刻
4. **单号引用链**：单据之间用单号互相串（处方单引用挂号单号）
5. **主子表**：一张主单下挂明细行（挂号单挂收费明细）

**产出**：候选单据清单、状态机、流程模板；当库里有**流转历史表 / 操作日志表**时，可额外还原实例路径（某次就诊具体走过哪几步）。

**置信度与校正预期**：
- 引擎对每个识别结果给出**置信度**，低置信度节点/边在草稿图上标记，供人优先校正。
- 对陌生库的自动识别是**近似**（命中率约 60~85%，视库规范程度浮动）→ 引擎产出的本质是**待校对稿**。
- 素材渠道补充：连库扫描（主）＋ 导入 E-R 图 / 设计文档解析（补）＋ 人工创建（兜底），三渠道汇入同一底图统一校正。

### 15.4 引擎分析后的主动分流（人在前端选择）

**引擎出第一版草稿图 → 前端渲染可见 → 用户亲眼看过草稿后，在前端主动选择下一步：**

1. **草稿够用** → 直接进人工校正（省一次大模型调用，快）
2. **草稿不够** → 加一道**大模型细化**（在引擎草图上补语义，准）
3. **草稿太乱** → 作废重来（换路线②大模型直接分析，或换来源）

**可回退**：选了「加大模型细化」后对结果不满意，可回到纯引擎草稿重新校正；选错路线也能重来。

> **原则：主动权在人，不在系统。** 系统不做「自检/裁决」（避免「开盲盒」），只负责把草稿清楚呈现；选不选大模型、怎么选，全部由用户在可见草稿上判断决定。

### 15.5 大模型分析（路线②）与接入层

**路线② 直接分析**：库连不上或结构太乱时，大模型直接以原始素材（库结构 / 界面入口 / 导入文档）为输入从头分析出图。产出同样是提案，最终人工拍板。

**模型接入层（可插拔模型市场）**：
- 平台**封装一层模型接入层**，可同时接入多个大模型（如 DeepSeek / 通义 / Claude / GPT 等），各自配置 API Key / 地址 / 参数。
- 分析时**随意切换模型，不重跑流程**（类比：在 Claude Code 里随时切换不同模型）。
- 区分两层概念，**分开设计、不混淆**：
  - **模型层**：管「用哪家大模型」——可插拔、可替换、可对比。
  - **路线层**：管「走不走大模型」——入口路线选择。

**调用与可信度约束**（建议）：
- 通用 API 按 token 计费，调用策略「**先小样验证、再全量分析**」。
- 大模型可能一本正经说错 → 输出始终**经人工校验**夹一道，不直接改库。

### 15.6 工作流（图来源管线）

```
图来源入口 → 选路线（引擎 / 大模型 / 人工）
  → 引擎路线：出草稿后由用户在前端主动选择「是否加一道大模型细化」
      （够用 → 直接人工校正 / 不够 → 加大模型 / 太乱 → 作废重来）
  → 统一人工校正（唯一拍板环节）
  → 准底图
```

- 引擎 / 大模型产出的都是**提案/草稿**，最终判断权在**人工校正**（唯一拍板环节）。
- **大模型介入时机由人灵活掌握**（入口处 + 引擎分析后均可），不由系统自动裁决。

### 15.7 三层视图（图怎么用）⭐ 设计框架

同一套关系网，可按三个**层面**查看，像导航软件的三张地图，可叠加：

| 视图 | 画的是什么 | 类比 | 用途 |
| --- | --- | --- | --- |
| **数据流视图**（表级血缘） | 表 → 表，数据怎么流动、汇到哪 | 地下**管线图** | 数据核实、血缘溯源 |
| **业务流视图**（系统级） | 系统 → 系统，请求/业务怎么走、谁依赖谁 | 地面**路网图** | 流程展示、择路、摸瓜 |
| **融合视图** | 一个业务场景背后对应哪些表、数据走什么路 | 导航**图层叠加** | 场景 ↔ 数据对应，一查到底 |

**与现有建模体系衔接**（建议）：
- 三种视图是对**同一节点/边集合**的不同投影；节点类型仍沿用现有 4 类混合体系（SYSTEM / TABLE / ACTION …），不另起一套。
- 起步**先做前端投影**：按视图过滤 / 分组节点类型展示（代价最小）；「层（Layer）」作为独立建模概念（可选）后置。

### 15.8 校正闭环经验沉淀（越用越准）⭐ 设计框架

- **人工校正内容**：改名、确认单据 / 字段类型、合并节点、增删节点/边、确认流程顺序。
- **沉淀**：校正结果回写「模式库 / 领域库」——同一系统越校越准，同类系统可复用经验（如多家医院 HIS）。
- **效果**：引擎「出提案」越来越准，人工校正工作量递减。
- **实施**（建议）：先做**校正记录留存**（最简版），「反馈学习」后置。
- **定位**：这是通用方案成立的支点——**引擎负责快、人负责准、闭环负责越用越准**。

### 15.9 设计底线

1. 大模型**不直接产出最终图**，只产出提案，最终判断权在人工校正（防止脏图直接变「准图」，保住闭环）。
2. **不接大模型，平台照常工作**（引擎 + 人工闭环）。
3. **成本与隐私**：通用 API 按 token 计费，调用策略「先小样验证、再全量分析」；医院等敏感场景可切本地/私有化模型。

### 15.10 里程碑与实施顺序（指导落地）

| 阶段 | 交付 | 验证方式 |
| --- | --- | --- |
| **G1 三层视图定型** | 数据模型 + 前端投影（图怎么用） | 现有真实路网按三层视图切换展示 |
| **G2 图来源管线原型** | 前端交互原型（假数据模拟 15.4 主动分流） | 手工点选「够用 / 加大模型 / 作废重来」看手感 |
| **G3 引擎最小可行版** | 拿现有 H2 / MySQL 真实库跑「单据模式库」识别，**实测置信度** | 识别准确率数字回填本节与校正环节设计 |
| **G4 大模型接入层** | 可插拔接入层 + 至少一个供应商验证 | 切换模型重跑对比 |
| **G5 校正闭环** | 校正记录留存 + 沉淀（最简版） | 二次识别同一库校正量下降 |

> 顺序原则：**先定型「图怎么用」→ 再看「图怎么来」交互 → 再落引擎 → 再接大模型 → 最后沉淀**。G1 决定数据结构，排最前；G3 用真实库实测，避免纸上谈兵。

### 15.11 已确认决策 vs 默认建议

**已确认（决策 #15，见 14.1）**：三条路线入口选择；引擎分析后由用户前端主动选择是否加大模型细化；统一人工校正为准；大模型可插拔接入、随意切换；引擎定骨架、大模型管语义、人拍板；不接大模型也照跑。

**默认建议（待评审，按此执行可调整）**：
- 三层视图起步**先做前端投影**，不做独立「层」概念。
- 校正沉淀**先做记录留存**，「反馈学习」后置。
- 引擎识别**优先用单据模式库**（主键 / 编码号 / 状态 / 时间 / 引用链 / 主子表）。
- 实施顺序 **G1 → G5**。

-- ==================== 建模域 ====================

-- 站点节点（系统/库表/部门岗位/业务动作/制造设备等）
CREATE TABLE node (
  id            BIGINT       NOT NULL AUTO_INCREMENT,

  code          VARCHAR(50),            -- 唯一编码

  description   VARCHAR(500),
  ext           JSON,
  created_at    DATETIME     NOT NULL,
  updated_at    DATETIME     NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_node_code (code),
  KEY idx_node_type (node_type),
  KEY idx_node_name (name)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 路网边（站点间有向连接，支持分岔/汇合）
CREATE TABLE relation (

  status        VARCHAR(20)  DEFAULT 'ACTIVE',
  created_at    DATETIME     NOT NULL,
  updated_at    DATETIME     NOT NULL,
  PRIMARY KEY (id),

) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

  PRIMARY KEY (id),

) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

  description VARCHAR(500),
  status      VARCHAR(20)  DEFAULT 'ACTIVE',
  created_at  DATETIME     NOT NULL,
  updated_at  DATETIME     NOT NULL,
  PRIMARY KEY (id),
  KEY idx_route_process (process_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 路线站点（有序，含该环节标准时长 SLA，卡点判定依据）
CREATE TABLE route_node (

  node_id      BIGINT NOT NULL,

) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

  enabled    TINYINT      DEFAULT 1,
  created_at DATETIME     NOT NULL,
  updated_at DATETIME     NOT NULL,

) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
